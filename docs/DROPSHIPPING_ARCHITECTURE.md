# MansooriKart Dropshipping Architecture

Phase G: hybrid fulfilment. MansooriKart sells both goods it owns and holds in its own
warehouses, and goods a supplier ships directly to the customer. Everything below describes
the implemented `/api/v1` runtime (`backend/src/services/dropshipService.ts`,
`backend/src/services/publicationService.ts`, `backend/src/routes/v1/adminDropshipFulfillments.ts`,
`backend/src/config/dropshipping.ts`). The frozen legacy `/api/*` runtime is untouched, and no
frontend was built in this phase.

**Inventory authority is unchanged.** `InventoryBalance` remains the authority for
MansooriKart-owned physical stock, `Product.stock` remains a service-maintained compatibility
mirror of owned stock, and every owned unit still moves through `adjustStock`. Dropshipping adds
no second stock authority and writes no `InventoryBalance` or `InventoryMovement` records. See
[INVENTORY_ARCHITECTURE.md](./INVENTORY_ARCHITECTURE.md).

Companion documents: [CSV_CATALOG_IMPORT_ARCHITECTURE.md](./CSV_CATALOG_IMPORT_ARCHITECTURE.md)
for how supplier catalogues arrive, [PRICING_ARCHITECTURE.md](./PRICING_ARCHITECTURE.md) for how
selling prices are derived.

## 1. This is dropshipping, not a marketplace

A `Supplier` remains the operational contact record introduced by purchasing. Phase G adds no
supplier login, no vendor dashboard, no seller storefront, no commission, and no payout or
settlement account. A supplier is a party MansooriKart buys from and asks to ship; it is never a
merchant account or a user of the system. Suppliers have no credentials in the schema at all, so
there is nothing for a supplier to authenticate against.

## 2. One canonical product, two fulfilment types

`fulfillmentType` lives on the existing canonical `Product`:

| Value       | Meaning                                                           |
| ----------- | ----------------------------------------------------------------- |
| `OWN_STOCK` | MansooriKart holds the units. Existing warehouse flow, unchanged. |
| `DROPSHIP`  | A supplier holds the units and ships them to the customer.        |

The default is `OWN_STOCK`, so every product that existed before this phase keeps behaving
exactly as it did. There is deliberately **no** `DropshipProduct`, `AdminProduct`, or
supplier-product-as-customer-product collection: the storefront, cart, wishlist, orders, reviews,
search, and reporting all continue to read one `Product` collection, and fulfilment type is an
attribute of it rather than a fork in the model.

Phase G also adds `sourceType` (`MANUAL` | `SUPPLIER_CSV`), `sellingPriceOverridden`,
`supplierSuggestedRetailPrice`, `publishedAt`, and `publishedBy` to `Product`. None of them are
customer-facing (§7 below).

## 3. Supplier catalogue records

`SupplierCatalogItem` (collection `suppliercatalogitems`) is the sourcing record binding one
supplier's line to one MansooriKart product:

`supplier`, `product`, `supplierSku`, `supplierProductName`, `supplierCost`, `currency`,
`supplierStock`, `supplierAvailability`, `supplierStockUpdatedAt`, `sourceRowHash`,
`sourceExternalId`, `sourceImageUrls`, `lastImportedAt`, `isActive`, `metadata`, timestamps.

`{ supplier, supplierSku }` is **unique**. That single index is what makes repeated imports safe:
the same supplier SKU can never silently create a second product, because the second attempt
resolves to the existing sourcing record and updates it. A product may carry several sourcing
records (several suppliers offering the same item); a supplier SKU resolves to exactly one.

Supplier-specific attributes that are not canonical MansooriKart catalogue fields — weight,
colour, size, barcode — are stored in `metadata` on this record, not invented as `Product`
fields. Unmapped supplier columns are ignored entirely.

**This record is the only home for supplier stock.** No `InventoryBalance` document is ever
created to represent units a supplier holds, and a supplier feed never produces an
`InventoryMovement`. A dropship product's own `Product.stock` stays at 0 because MansooriKart
owns none of it.

## 4. Server-owned identity

`Product.sku` is generated by the server (`MK-…`) and is the MansooriKart identity of the item.
`supplierSku` is the supplier's own string (`ABC-882819`) and is only ever a lookup key inside
`SupplierCatalogItem`. Nothing in the runtime treats a supplier SKU as the canonical identifier,
and a client cannot set `Product.sku` on an imported product — the import generates it, and the
admin catalog schemas are `.strict()` allowlists that exclude the server-owned fields.

Likewise `Order.orderNumber` remains the order identity. `supplierOrderReference` records what a
supplier calls the job on their side; nothing keys off it.

## 5. Supplier stock is advisory, and says so

`supplierAvailability` is one of `IN_STOCK`, `LOW_STOCK`, `OUT_OF_STOCK`, `UNKNOWN`, derived from
the reported quantity (`LOW_STOCK` at or below `SUPPLIER_LOW_STOCK_THRESHOLD` = 5 units; a row
with no quantity at all is `UNKNOWN`, not `OUT_OF_STOCK`).

Because it originates from a CSV a supplier uploaded at some point in the past, it is **not a
transactional guarantee**. Freshness is therefore exposed rather than hidden:
`supplierStockUpdatedAt` is returned alongside a centrally defined staleness threshold,
`SUPPLIER_STOCK_STALE_AFTER_HOURS` = 48 (`backend/src/config/dropshipping.ts`), and every admin
surface that shows supplier stock also shows `isSupplierStockStale`. A missing or unparseable
timestamp counts as stale.

## 6. Availability at cart and checkout

`BLOCKING_SUPPLIER_AVAILABILITY` is a single-entry allowlist: `['OUT_OF_STOCK']`. Only an
explicit out-of-stock signal blocks a purchase.

| Situation                                         | Cart                        | Checkout                   |
| ------------------------------------------------- | --------------------------- | -------------------------- |
| `OWN_STOCK`, quantity above `Product.stock`       | `409 INSUFFICIENT_STOCK`    | `409 STOCK_UNAVAILABLE`    |
| `DROPSHIP`, no active sourcing record             | `409 SUPPLIER_UNAVAILABLE`  | `409 DROPSHIP_UNAVAILABLE` |
| `DROPSHIP`, every active source `OUT_OF_STOCK`    | `409 SUPPLIER_OUT_OF_STOCK` | `409 DROPSHIP_UNAVAILABLE` |
| `DROPSHIP`, `UNKNOWN` or stale-but-positive stock | allowed                     | allowed                    |

A feed that reports no quantity is not evidence of absence, so `UNKNOWN` and stale-but-positive
stock are advisory and do not block. Staleness alone never blocks a sale; it is surfaced to the
operator instead.

## 7. Mixed orders and frozen line snapshots

One cart may contain own-stock lines and lines from several suppliers. Nothing separates them at
checkout; the order is created once, and each `Order.items` entry carries its own fulfilment
snapshot:

```
fulfillmentType   OWN_STOCK | DROPSHIP        (as at the moment of purchase)
supplier          the sourcing supplier        (DROPSHIP only)
supplierSku       the supplier's SKU           (DROPSHIP only)
supplierCost      supplier cost per unit       (DROPSHIP only)
unitCost          supplierCost for DROPSHIP, Product.costPrice for OWN_STOCK
lineCost          unitCost * quantity
```

Only `OWN_STOCK` lines call `adjustStock`, so a mixed order decrements warehouse stock for its
owned lines and leaves the dropship lines entirely outside the inventory ledger. A dropship line
produces **zero** `InventoryMovement` records.

These snapshots are historical fact and are never recomputed. Changing a product's
`fulfillmentType`, its `costPrice`, its selling price, or the supplier / supplier SKU /
supplier cost on the sourcing record afterwards does not rewrite a placed order line. When no
cost is known for a line, no cost snapshot is written at all rather than a misleading zero.

## 8. Supplier obligations: `DropshipFulfillment`

Because one order can involve several suppliers, the obligation cannot live on the order.
`DropshipFulfillment` (collection `dropshipfulfillments`) is one supplier's shipment obligation
for part of one order:

`fulfillmentNumber`, `order`, `orderNumber`, `orderItems` (zero-based indices into
`Order.items`), `supplier`, `status`, `supplierOrderReference`, `supplierTrackingNumber`,
`carrier`, `trackingUrl`, `sentToSupplierAt`, `confirmedAt`, `shippedAt`, `deliveredAt`,
`failedAt`, `cancelledAt`, `notes`, `statusHistory`, `createdBy`, `updatedBy`, timestamps.

`fulfillmentNumber` is server-generated as `DSF-YYYYMMDD-XXXXXX` and is unique. A collision is
retried with a fresh suffix (five attempts, then `500 DROPSHIP_FULFILLMENT_FAILED`); a client
cannot supply one.

### Creation at checkout

Dropship lines are grouped by supplier and one fulfillment is created per supplier, inside the
same compensated block that creates the order. Three things make that reliable:

- `{ order, supplier }` is **unique**, so a retry cannot add a second obligation for the same
  supplier on the same order. A duplicate-key error on that index is treated as success.
- A failure anywhere in the block removes the order, its coupon redemption, and its fulfillments,
  and reverses every stock deduction as a `CANCELLATION` movement — no half-created order and no
  orphan supplier obligation survives.
- Checkout requires an `Idempotency-Key`, so a replayed request returns the original order and
  the original fulfillments rather than creating more.

A `DropshipError` raised during creation surfaces to the customer as `409 DROPSHIP_UNAVAILABLE`.

When several sourcing records could serve a line, selection is deterministic: lowest supplier
cost, then oldest record, then id.

## 9. Supplier-side state machine

| From                 | Allowed next                                                    |
| -------------------- | --------------------------------------------------------------- |
| `PENDING`            | `SENT_TO_SUPPLIER`, `SUPPLIER_CONFIRMED`, `FAILED`, `CANCELLED` |
| `SENT_TO_SUPPLIER`   | `SUPPLIER_CONFIRMED`, `SHIPPED`, `FAILED`, `CANCELLED`          |
| `SUPPLIER_CONFIRMED` | `SHIPPED`, `FAILED`, `CANCELLED`                                |
| `SHIPPED`            | `DELIVERED`, `FAILED`, `CANCELLED`                              |
| `DELIVERED`          | terminal                                                        |
| `FAILED`             | terminal                                                        |
| `CANCELLED`          | terminal                                                        |

Each transition is claimed atomically (`findOneAndUpdate` on `{ _id, status: from }`), so two
concurrent operators cannot both advance the same fulfillment — the loser gets
`409 DROPSHIP_FULFILLMENT_CONFLICT`. An illegal move is `409 DROPSHIP_TRANSITION_INVALID` and
writes nothing. Re-sending the current status is an accepted no-op that appends no history.
Every accepted transition stamps its stage timestamp, appends a `statusHistory` entry
(`{ from, to, reason, actor, at }`), and writes an `AuditLog` record.

**This lifecycle is independent of `Order.orderStatus`.** The customer-facing order workflow
(`PENDING` → `CONFIRMED` → … ) is unchanged and is not driven by supplier progress: shipping one
supplier's half of a mixed order does not mark the customer's order shipped. Admin surfaces show
both.

## 10. Tracking

`carrier`, `supplierTrackingNumber`, and `trackingUrl` are operator-entered. A `trackingUrl` must
parse as an absolute `http`/`https` URL — a relative path or a `javascript:` scheme is
`400 TRACKING_URL_INVALID` and leaves the stored value untouched. The URL is stored for a human
to click and is **never fetched server-side**.

`notes` are internal. Neither notes nor `supplierCost` appear on any customer-facing serializer.

## 11. Cancellation records intent, not a supplier action

`GET /api/v1/admin/dropship-fulfillments/cancellation-policy` documents, per status, what
cancelling actually means:

| Status               | `requiresSupplierContact` |
| -------------------- | ------------------------- |
| `PENDING`            | `false`                   |
| `SENT_TO_SUPPLIER`   | `true`                    |
| `SUPPLIER_CONFIRMED` | `true`                    |
| `SHIPPED`            | `true`                    |

A `PENDING` fulfillment was never transmitted anywhere, so cancelling it is purely internal. In
every other state MansooriKart has already told the supplier something, and setting the status to
`CANCELLED` **records MansooriKart's own intent only** — it does not cancel anything at the
supplier and the API never claims it did. Stopping a shipment that is already moving requires
contacting the supplier out of band. There are no fake external side effects anywhere in this
module.

Cancelling the customer order cascades: every fulfillment still in `PENDING`,
`SENT_TO_SUPPLIER`, `SUPPLIER_CONFIRMED`, or `SHIPPED` is moved to `CANCELLED` with the reason
recorded, terminal ones are left alone, and own-stock lines are restocked exactly as before.

## 12. Two distinct workflows, deliberately not merged

| `PurchaseOrder` + `GoodsReceipt`           | `DropshipFulfillment`                       |
| ------------------------------------------ | ------------------------------------------- |
| MansooriKart buys stock for itself         | A supplier ships to a customer              |
| Goods arrive at a warehouse                | Goods never touch a MansooriKart warehouse  |
| Writes `InventoryBalance` + movements      | Writes no inventory records at all          |
| Exists before any customer order           | Exists only because a customer ordered      |
| Cost authority for `OWN_STOCK` `costPrice` | Carries the per-line supplier cost snapshot |

Procurement remains the cost authority for owned stock: a supplier CSV never overwrites
`costPrice` on an `OWN_STOCK` product. See
[PURCHASING_ARCHITECTURE.md](./PURCHASING_ARCHITECTURE.md).

Returns and refunds are likewise unchanged — the existing `Return` and `Refund` authorities
handle a dropship order like any other, and no parallel return domain was created. Supplier-side
accounting settlement (recovering cost from a supplier for a returned dropship item) is out of
scope for this phase.

## 13. Publication: the gate between imported and on sale

`Product.status` carries publication state, reusing the values the catalogue already had rather
than adding a parallel flag:

| Status     | Public catalogue | Purchasable |
| ---------- | ---------------- | ----------- |
| `DRAFT`    | no               | no          |
| `ACTIVE`   | yes              | yes         |
| `ARCHIVED` | no               | no          |

Enforcement is in the backend, not the UI. Public product listing, product detail, search,
category and brand browsing, related products, reviews, cart, wishlist, and checkout all resolve
products through an `ACTIVE`-only filter, so a `DRAFT` product cannot be listed, fetched, added to
a cart, or bought by guessing its id.

`publishProducts` is the only path from `DRAFT` to `ACTIVE`. It refuses a product that is missing
a name, a MansooriKart SKU, a description, an image, a selling price greater than zero, or a real
category (an imported row still sitting on the `Uncategorized` placeholder is not classified yet,
and an archived category is not a destination), that has an unrecognised fulfilment type, or that
is `DROPSHIP` with no active supplier source — a dropship product with nobody to ship it could
otherwise accept an order MansooriKart cannot fulfil. Every reason is returned as a list, so an
operator fixes a draft in one pass. A bulk request publishes what passes and reports the rest
untouched; a single-product request turns any rejection into a `400` so it never silently no-ops.

The admin catalog create/update endpoints accept `status`, so they run the same checks — there is
no second door into `ACTIVE`.

Archiving needs no validation (pulling an incomplete product is exactly what it is for), clears
`featured`, and deliberately leaves the sourcing record active so a later import updates it
instead of creating a duplicate.

## 14. What a customer can see

Customer-facing serializers are allowlists, and the fields this phase added are absent from all of
them. A shopper's product, cart, wishlist, and order payloads never contain `supplierCost`,
`costPrice`, `unitCost`, `lineCost`, gross margin, `fulfillmentType`, `sourceType`,
`sellingPriceOverridden`, `supplierSku`, a supplier name or id, a fulfillment number, or any
pricing-rule internals. A customer order line exposes `productId`, `name`, `sku`, `image`,
`unitPrice`, `quantity`, and `lineSubtotal` only.

The same order viewed through `GET /api/v1/admin/orders/:id` does carry the fulfilment snapshots
and the order's `dropshipFulfillments`, because that surface is `SUPER_ADMIN`-only.

## 15. Cost of goods

A `DROPSHIP` line's `unitCost` snapshot is the supplier cost at the moment of purchase; an
`OWN_STOCK` line's is `Product.costPrice`. Both feed the _same_ `unitCost` / `lineCost` fields the
Phase F finance module already reads, so COGS and gross-profit reporting need no second formula
and no fulfilment-type branch.

Margin figures are labelled **gross merchandise margin** wherever they appear: selling price minus
supplier cost, nothing else. They exclude shipping, payment fees, returns, refunds, and every
operating expense, and are not final business profit. Phase F remains the authority for that. See
[FINANCE_ARCHITECTURE.md](./FINANCE_ARCHITECTURE.md).

## 16. Admin API surface

All routes are `SUPER_ADMIN`-only (`requireAuth` + `requireSuperAdmin`): no token is `401`, a
`CUSTOMER` token is `403`. Query and body schemas are `.strict()`.

| Method  | Path                                                      | Purpose                                  |
| ------- | --------------------------------------------------------- | ---------------------------------------- |
| `GET`   | `/api/v1/admin/supplier-sources`                          | Sourcing records, filtered and paginated |
| `GET`   | `/api/v1/admin/products/:productId/supplier-sources`      | Every supplier offering one product      |
| `GET`   | `/api/v1/admin/supplier-sources/:id`                      | One sourcing record with freshness       |
| `POST`  | `/api/v1/admin/products/publish-preview`                  | Publication validation, writes nothing   |
| `POST`  | `/api/v1/admin/products/publish`                          | Publish selected                         |
| `POST`  | `/api/v1/admin/products/:id/publish`                      | Publish one                              |
| `POST`  | `/api/v1/admin/products/archive`                          | Withdraw from sale                       |
| `GET`   | `/api/v1/admin/dropship-fulfillments/cancellation-policy` | What cancelling means, per status        |
| `GET`   | `/api/v1/admin/dropship-fulfillments`                     | List by supplier, status, order, date    |
| `GET`   | `/api/v1/admin/dropship-fulfillments/:id`                 | Detail, allowed transitions, timeline    |
| `PATCH` | `/api/v1/admin/dropship-fulfillments/:id`                 | Advance status, set tracking             |

There is **no** create route for a fulfillment: obligations exist because a customer ordered, so
`POST /dropship-fulfillments` is a `404`. The `PATCH` body accepts only `status`,
`supplierOrderReference`, `supplierTrackingNumber`, `carrier`, `trackingUrl`, `notes`, and
`reason`, and must be non-empty. Everything server-owned is rejected before any database access:
`fulfillmentNumber`, `order`, `orderNumber`, `orderItems`, `supplier`, the stage timestamps,
`statusHistory`, `createdBy`, and `updatedBy` are all `400 VALIDATION_ERROR`.

Listing is bounded (`limit` ≤ 100, sortable only on `createdAt`, `updatedAt`, `status`,
`fulfillmentNumber`) and returns `page` / `limit` / `total` / `totalPages` meta. Fulfillment
payloads carry no supplier cost or margin.

## 18. Audit

`DROPSHIP_FULFILLMENT_CREATED` (one entry per checkout, listing order number, suppliers, and
fulfillment numbers), `DROPSHIP_FULFILLMENT_STATUS_CHANGED`, `DROPSHIP_FULFILLMENT_TRACKING_UPDATED`,
`PRODUCT_PUBLISHED` / `PRODUCT_BULK_PUBLISHED`, `PRODUCT_ARCHIVED` / `PRODUCT_BULK_ARCHIVED`, and
the order-cancellation entries which record how many fulfillments were cancelled with them.

Audit metadata holds identifiers and counts, capped at 50 ids per entry. Internal operator notes
are not copied into audit metadata.

## 19. Deferred

Supplier API and marketplace-feed integrations (CSV is the only ingestion path in this phase),
supplier logins and any vendor-facing surface, supplier payout / commission / settlement,
supplier-side accounting for returns, automated supplier order transmission (a fulfillment records
that MansooriKart sent an order; it does not send one), automatic stock synchronisation on a
schedule, and all frontend work.
