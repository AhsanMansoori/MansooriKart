# MansooriKart Core API Contract

All v1 endpoints return `{ "success": true, "data": ... }`; product lists also return pagination `meta`. Errors return `{ "success": false, "error": { "code", "message" }, "requestId" }`.

## Authentication

The official v1 header is `Authorization: Bearer <JWT>`. Registration accepts name, email and password and always creates `CUSTOMER`. Local and Google sign-in issue the same stateless JWT for 15 minutes by default and never longer than one hour. Reset tokens are hashed, expiring, atomically single-use, and reset invalidates earlier JWTs through `sessionVersion`. There is no refresh endpoint; browser logout removes local token material.

## Profile and addresses

`GET /api/v1/me` returns the authenticated user. `PATCH /api/v1/me` accepts only name, phone and HTTPS avatar. Email, roles, password and internal/security fields are rejected.

Addresses use `/api/v1/me/addresses`. Ownership is scoped in each database query. Marking an address default unsets only the caller's other default; deleting the default promotes the caller's most recently updated remaining address.

## Catalog

Categories, brands and products are public active-only reads. Products support page, limit (1–100), search (escaped and bounded to 80 characters), category, brand, price bounds, featured and whitelisted sorting (`newest`, `price_asc`, `price_desc`, `rating`). Product detail accepts a slug or valid Mongo ObjectId.

## Super Admin core and catalog

All `/api/v1/admin/*` endpoints require a current `SUPER_ADMIN` Bearer token. `GET /api/v1/admin/dashboard` returns real product, order, customer, low-stock, recent-order, and realized-revenue data. Realized revenue retains collected delivered and return-stage orders through partial or full refund state; refund records are then subtracted once. Unpaid COD, cancelled, and failed orders are excluded.

`GET /api/v1/admin/audit-logs` supports safe pagination and action, resource type, actor, and date filters. It serializes safe audit fields only. `GET /api/v1/admin/system/health` returns status, database connection state, uptime, environment name, and optional application version without configuration values or credentials.

Admin catalog CRUD/archive routes are implemented for products, categories, brands, product types, generic attributes/values, and product badges. Product DELETE archives rather than physically removes a record. Product create/update uses strict request allowlists, escaped/bounded search, whitelisted sorting, safe pagination, and stable duplicate codes (`PRODUCT_SKU_EXISTS`, `SLUG_EXISTS`). Public catalog serializers never return cost price, stock, SEO, audit data, or admin-only status fields.

Size and color are generic `CatalogAttribute` kinds. Weight is deferred because the current sellable Product is the sole inventory authority. Product bases and product variants are deferred: the current cart, checkout, order snapshot, and inventory contract is product-level and is not variant-aware, so adding independent variant stock now would create conflicting inventory authorities. Product media metadata is implemented through `images` (`url`, `alt`, `position`, `isPrimary`); binary storage and provider selection remain deferred.

## Inventory ERP

Warehouse-aware inventory uses `InventoryBalance` as the target stock authority, keyed by product, warehouse, and location. Available stock is server-derived as on-hand minus reserved; launch reservations are zero/deferred. `Product.stock` is retained only as a service-maintained compatibility mirror. Existing products are lazily and idempotently backfilled into the default `MAIN` warehouse and `PRIMARY` location when inventory is first used.

Super Admin inventory APIs support warehouse/location CRUD and archival, balances, stock detail/listing, safe movement history, explicit adjustments, and idempotent transfers. Mutations use strict request allowlists and emit AuditLog records. Transfers require `Idempotency-Key`, reject self-transfers and insufficient source availability, preserve total stock, and produce immutable paired transfer movements. Online checkout fulfils from the default warehouse.

## Not implemented yet

Data and report **export** — CSV download, XLSX generation, scheduled delivery — and expanded OpenAPI are deferred. Supplier CSV **import** is implemented and runs in the opposite direction: it reads a supplier file into `DRAFT` products and exports nothing. See "CSV catalog import" below.

## Commerce foundation

Cart and wishlist require `Authorization: Bearer <JWT>`. Cart writes accept only product IDs and positive integer quantities. Cart prices and subtotals are recalculated from current products and cart operations do not reserve or decrement stock. Guest merge has a **partial** policy: duplicate guest lines are aggregated; each infeasible item is omitted and returned with an issue code, while feasible items are merged.

Coupon preview accepts only a code and recalculates the authenticated user's cart subtotal. Codes normalize to uppercase. Percentage and fixed discounts use two-decimal rounding, honour dates, enabled state, minimums, limits and maximum discount, and cannot reduce the subtotal below zero. Preview does not increment usage. Checkout enforces global and per-customer limits transactionally; failure or a losing concurrent request consumes no capacity. Cancellation retains redemption history and does not restore coupon capacity.

Inventory adjustments are Super Admin-only and require a non-zero integer delta and bounded reason. Balance, `Product.stock` compatibility mirror, movement, transfer and audit writes commit in one MongoDB transaction; a fault leaves none applied. Low-stock and out-of-stock endpoints aggregate available inventory (`quantityOnHand - quantityReserved`) across all balances for a product. Real replica-set tests cover persistence faults and one-unit competing-decrement cases.

Super Admin coupon DELETE is a soft archive: the record remains and `enabled` becomes false. Admin inventory/coupon mutations write safe AuditLog records.

## Checkout and orders

`POST /api/v1/checkout/preview` accepts a saved address, optional coupon, COD, and selected cart quantities, then returns server-derived PKR subtotal, discount, shipping, tax, payable total, and a quote hash. `POST /api/v1/checkout` confirms that quote with an `Idempotency-Key`. Prices, availability, totals, and order numbers remain server-derived. COD begins `UNPAID`. Configuration changes never rewrite an order snapshot.

Checkout commits the order, coupon redemption, stock, fulfillment, selected cart quantities and audit together. Cancellation is allowed from `PENDING` and `CONFIRMED` and commits state, stock restore, supplier-cancellation intent and audit exactly once. Admin transitions are `PENDING→CONFIRMED/CANCELLED`, `CONFIRMED→PROCESSING/CANCELLED`, `PROCESSING→SHIPPED`, `SHIPPED→DELIVERED`; COD payment collection is `UNPAID→PAID`.

Checkout also persists a server-generated `invoiceNumber` and fires a post-commit order confirmation email. See [ORDERS_SALES_ARCHITECTURE.md](./ORDERS_SALES_ARCHITECTURE.md) for the full state machines and invariants.

## Reviews and ratings

`GET /api/v1/products/:productId/reviews` is public and returns only `PUBLISHED` reviews with pagination and whitelisted `newest`, `oldest`, `highest-rating`, or `lowest-rating` sorting. Public entries expose only review ID, rating, title, body, verified-purchase flag, creation time, and reviewer display name—never email, credentials, addresses, order/payment details, moderation metadata, or audit data.

Authenticated customers create reviews with only `rating`, optional `title`, and `body`. Ratings are integer 1–5; title is 1–120 trimmed characters when supplied; body is 3–2,000 trimmed characters. Product identity comes from the route, customer identity and mutation ownership come from the JWT, and only `ACTIVE` products are reviewable. Customer PATCH accepts the same editable fields; DELETE physically removes only the caller's persisted review.

There is one review per customer/product. A compound unique database index on `customer + product` is initialized before review writes and is the race-safe authority; duplicate attempts return `409 REVIEW_EXISTS` without exposing Mongo duplicate-key details. `verifiedPurchase` is server-derived: it is true only if the customer has a persisted `DELIVERED` Order containing the product; non-purchasers may still review with the flag false.

Reviews begin `PUBLISHED`. Super Admin may use `PATCH /api/v1/admin/reviews/:reviewId/status` with only `status` (`PUBLISHED` or `HIDDEN`) and `reason`; moderation is audited. Hidden reviews are excluded from public results and product aggregates. `ratingAverage` (rounded to two decimals) and `ratingCount` are server-maintained from published reviews and recalculated after create, edit, delete, hide, and republish. All review inputs are strict allowlists and use the standard v1 error envelope.

## Orders and sales ERP

Full design notes live in [ORDERS_SALES_ARCHITECTURE.md](./ORDERS_SALES_ARCHITECTURE.md).

`GET /api/v1/admin/orders` is Super Admin-only with a strict query allowlist: pagination, `orderNumber` (upper-cased exact), `customer` (exact email or name lookup — never a regex), `orderStatus`, `paymentStatus`, `paymentMethod`, `from`/`to`, `minAmount`/`maxAmount`, and whitelisted `sort`/`direction`. Operator objects and unknown keys are rejected with `VALIDATION_ERROR` before reaching Mongo; `__proto__` keys are stripped by the query parser and neither filter nor pollute. Order detail populates the customer as `name` and `email` only. Malformed IDs return `400 VALIDATION_ERROR` and unknown IDs `404 ORDER_NOT_FOUND`, with no `CastError`, driver text, or stack trace.

Cancellation is claimed with a single atomic conditional update before any restock, so a simultaneous customer and admin cancellation produces exactly one success, one `CANCELLATION` movement, one restored balance, and one audit record. Repeat cancellations return `400 ORDER_NOT_CANCELLABLE` and touch no inventory.

Returns require a `DELIVERED` order and follow `REQUESTED→APPROVED|REJECTED`, `APPROVED→RECEIVED`, `RECEIVED→COMPLETED`. Quantities are reserved against the purchased snapshot through `ReturnAllocation`, so the same unit cannot be claimed twice. **A return never restores sellable inventory**: no stage performs a restock and no `RETURN` movement is written. Returned units re-enter stock only through an explicit audited Inventory ERP adjustment after inspection.

Refunds are Super Admin-only ledger records; no payment provider is called. `POST /api/v1/admin/orders/:orderId/refunds` requires an `Idempotency-Key` and accepts only `amount`, `reason`, and optional `returnId`. A unique compound index on `(order, idempotencyKey)` is the durable idempotency authority: sequential and concurrent replays return one refund, and a replay cannot smuggle a different amount. The sum of non-`FAILED` refunds can never exceed `order.total`, enforced atomically by reserving headroom on `Order.refundedTotal` with an `$expr` conditional `$inc` before the refund is written; the loser of a cap race receives `400 REFUND_AMOUNT_INVALID`. Headroom is released on insert failure, duplicate key, and `FAILED` status.

Invoices are projections of the immutable order snapshot — product documents are never consulted, so post-purchase renames or repricing cannot alter a historical invoice. `invoiceNumber` is server-generated at checkout as `INV-<orderNumber>`, persisted, never client-settable, and never regenerated. `GET /api/v1/orders/:orderId/invoice` and `/invoice.pdf` are scoped to the caller's own orders (404 otherwise); the `/api/v1/admin/orders/:orderId` equivalents serve any order and expose the customer as `id`, `name`, `email` only. The `.pdf` routes return real pdfkit-rendered PDF bytes with `Content-Type: application/pdf`, an attachment `Content-Disposition` naming the invoice number, and an accurate `Content-Length`.

Order confirmation email is provider-agnostic; **no provider is integrated and no credentials are required**. The default adapter records intent only, and production wiring just calls `setEmailAdapter`. Delivery is a post-commit side effect that never throws: a provider outage is recorded as a safe bounded failure while the order, inventory, audit record, and emptied cart remain committed. The message is exactly `{ to, subject, template, data }` with `ORDER_CONFIRMATION` content built from the order snapshot — never passwords, JWTs, reset tokens, secrets, or the internal user object.

`GET /api/v1/admin/abandoned-carts` derives abandoned carts from persisted `Cart` documents with no duplicated data: at least one item and inactive past a threshold (default 24 hours, 1–2160 overridable). `estimatedValue` is recomputed from the current catalog price of `ACTIVE` products (`meta.valuation: CURRENT_CATALOG_PRICE`); a stored cart price is never authoritative. Anonymous carts are **deferred** because `Cart.user` is required and guest carts are not persistently identifiable — no anonymous identity is fabricated.

`GET /api/v1/admin/sales/dashboard` accepts either `range=7d|30d|90d` or both `from` and `to`. `grossSales` sums every order total; `realizedRevenue` retains collected delivered/return-stage sales across `PAID`, `PARTIALLY_REFUNDED`, and `REFUNDED`; `refunds` sums non-`FAILED` refund reservations. Net realized revenue subtracts refunds once. Unpaid COD and cancelled orders are excluded.

## Customers ERP

Full design notes live in [CUSTOMERS_ERP_ARCHITECTURE.md](./CUSTOMERS_ERP_ARCHITECTURE.md).

There is **no duplicate customer collection**. A customer is the existing `User` document with `role: CUSTOMER`; the ERP is a read model over the existing `Order`, `Address`, `Cart`, `Wishlist`, `Review`, `ReturnRequest`, and `Refund` architecture. Refunds carry no customer reference and are reached through the customer's own orders, so a refund cannot be attributed to the wrong account.

Only `name`, `email`, `phone`, `avatar`, `role`, `status`, `createdAt`, and `updatedAt` ever leave the ERP. Aggregation uses an explicit inclusive `$project` allowlist rather than relying on `select: false`, so password hashes, reset-token hashes, reset expiry, JWT material, and `__v` are structurally unable to appear in any response.

Statistics are real aggregates over `orders` and are never stored or client-supplied: `totalOrders` and `grossSpend` count every status, while `realizedSpend` sums only `DELIVERED` **and** `PAID` orders — the same condition as the sales dashboard, so lifetime value and realized revenue cannot disagree. Segments (`PROSPECT`, `NEW`, `REPEAT`, `VIP`, `AT_RISK`) are derived read-only reporting labels; nothing acts on them and no campaign, email, SMS, or push mechanism is attached.

`GET /api/v1/admin/customers` uses a strict query allowlist (pagination, `search`, `status`, `role`, `segment`, `hasOrders`, `from`/`to`, whitelisted `sort`/`direction`); `search` is regex-escaped so an operator-looking value matches literally, and unknown keys are `400 VALIDATION_ERROR`. `GET /api/v1/admin/customers/:id` returns a 360° view (statistics, addresses, recent orders, cart/wishlist summaries, reviews, returns, refunds). Malformed IDs are `400 VALIDATION_ERROR` and unknown IDs `404 CUSTOMER_NOT_FOUND`, with no `CastError` or driver text.

`PATCH /api/v1/admin/customers/:id/status` is the **only** mutation, and its strict body is exactly `{ status: ACTIVE|SUSPENDED, reason? }`. Suspending a `SUPER_ADMIN` or the caller's own account is `409 CUSTOMER_STATUS_FORBIDDEN`; a no-op is `409 CUSTOMER_STATUS_UNCHANGED`; both write no audit record. The write is a conditional `findOneAndUpdate` scoped to `role: CUSTOMER` and the observed status. `requireAuth` rejects a suspended user's existing token, so suspension takes effect immediately.

**Customer ERP is not a privilege-escalation path.** No generic `PATCH /api/v1/admin/customers/:id` route exists, `role` is absent from every schema in the router, no admin route anywhere writes `User.role`, and public registration always creates `CUSTOMER` even when a role is submitted.

## Purchasing ERP

Full design notes live in [PURCHASING_ARCHITECTURE.md](./PURCHASING_ARCHITECTURE.md).

Suppliers are an operational contact record only — **no bank account, IBAN, card, or portal credential field, and no supplier login**. `paymentTerms` (`PREPAID`, `COD`, `NET_7|15|30|45|60`) is descriptive, not a settlement instruction. Codes are uppercased and unique (`409 SUPPLIER_CODE_TAKEN`); DELETE archives rather than removes and is refused with `409 SUPPLIER_HAS_OPEN_ORDERS` while open purchase orders exist. Purchase orders may only be raised against an `ACTIVE` supplier.

Purchase orders move `DRAFT→PENDING_APPROVAL→APPROVED` and then through receiving; only `DRAFT` is editable (`409 PURCHASE_ORDER_NOT_EDITABLE`). `poNumber` is server-generated (`PO-YYYYMMDD-XXXXXX`) and never client-settable; `total`, `subtotal`, `status`, `statusHistory`, and every receiving counter are server-owned and rejected by the strict allowlists. Totals are always recomputed from lines, each product may appear once per order (`PURCHASE_ITEMS_DUPLICATED`), and neither creation nor approval moves stock.

`POST /api/v1/admin/purchase-orders/:id/receipts` requires an `Idempotency-Key` (8–128 chars, else `400 IDEMPOTENCY_KEY_REQUIRED`) and is eligible only for `APPROVED` or `PARTIALLY_RECEIVED` orders (`409 PURCHASE_ORDER_NOT_RECEIVABLE`). Line capacity is claimed for every requested line in a single `$expr` conditional update, so a mixed-validity multi-line receipt applies nothing and concurrent receipts can never jointly exceed the ordered quantity; over-receipt is `409 PURCHASE_RECEIPT_QUANTITY_INVALID` whether caught pre-flight or in the race, while a zero-quantity line is `400`. Unique compound indexes on `(purchaseOrder, idempotencyKey)` are the durable idempotency authority for receipts and returns: a first application is `201`, any replay is `200` returning the original document, a replay carrying a different body still returns the stored one, and three simultaneous same-key requests produce exactly one document.

**Only accepted received quantity increases stock**, and only through the existing inventory service (`type: PURCHASE_RECEIPT`, `referenceType: PurchaseOrder`). `InventoryBalance` remains the authority, `Product.stock` remains a synchronized mirror, and no purchasing code writes stock directly. Rejected units are recorded and never enter inventory; completeness is measured against delivered quantity (accepted + rejected).

Purchase-order counters, receipt/return documents, stock, cost snapshots and audit entries commit in one transaction. A persistence or audit fault leaves no partial counter, stock, document, movement, or artificial compensating movement. Failures surface as `500 PURCHASE_RECEIPT_AUDIT_FAILED` / `PURCHASE_RETURN_AUDIT_FAILED`, and the same idempotency key may succeed once the fault clears.

**Purchase returns are IMPLEMENTED, not deferred.** They are eligible only for `PARTIALLY_RECEIVED`, `RECEIVED`, or `CLOSED` orders, capped per line at `quantityAccepted - quantityReturned` (`409 PURCHASE_RETURN_QUANTITY_INVALID`) and capped again by the inventory service's non-negative balance guard (`INSUFFICIENT_STOCK`, surfaced as `409`, persisting nothing). No supplier refund, credit note, payable adjustment, or financial settlement is implied or recorded.

A purchase order with any received units cannot be cancelled (`409 PURCHASE_ORDER_NOT_CANCELLABLE`), enforced both before the transition table and as a filter condition on the atomic update; historical received inventory is never erased.

**Cost price policy is `LATEST_PURCHASE_COST`**: `Product.costPrice` becomes the latest accepted unit cost, with `previousCostPrice` recorded per receipt line and `costPriceSynced` on the receipt. **FIFO, LIFO, weighted average, and standard costing are explicitly NOT implemented** — there are no cost layers and no revaluation of existing stock. The sync is non-fatal; a failure flags the receipt instead of reverting physically received goods.

`GET /api/v1/admin/purchasing/dashboard` and `/reports` (`groupBy=supplier|product|date`) are live aggregates over suppliers, purchase orders, receipts, and returns — no fabricated numbers. `committedValue` and `receivedValue` are procurement commitments and goods-in values, declared as `basis: PROCUREMENT_COMMITMENT_AND_GOODS_IN`; they are **not** expenses, payables, cost of goods sold, or profit inputs, and no such field is returned. The Finance phase honours this boundary: an operating expense is an explicit `APPROVED` `Expense` record and nothing else, so raising or approving a purchase order still creates no expense. Accounts payable, supplier payment, and accounting journals remain deferred.

Audit records exist only for operations that actually succeeded (`SUPPLIER_CREATED`, `SUPPLIER_UPDATED`, `SUPPLIER_ARCHIVED`, `PURCHASE_ORDER_CREATED`, `PURCHASE_ORDER_UPDATED`, `PURCHASE_ORDER_<STATUS>`, `PURCHASE_GOODS_RECEIVED`, `PURCHASE_RETURN_CREATED`); refused cancels, rejected transitions, and unauthorized calls write nothing. No `CastError`, driver message, index name, or stack trace is ever returned.

## Finance ERP

Full design notes live in [FINANCE_ARCHITECTURE.md](./FINANCE_ARCHITECTURE.md).

`Expense` is the only new collection. It records money actually spent running the store: `EXP-YYYYMMDD-XXXXXX` (server-generated, never client-settable), one of fifteen operating categories, `amount` + `taxAmount` with server-derived `totalAmount`, `expenseDate`, `paymentMethod`, optional `supplier` and `purchaseOrder` cross-references, and `DRAFT → APPROVED → VOIDED` with an append-only `statusHistory`. **There is deliberately no salary or payroll category and no employee reference** — payroll is out of scope. There is no accounts-payable ledger, no double-entry journal, no chart of accounts, and no bank reconciliation.

Lifecycle: only a `DRAFT` is editable (`409 EXPENSE_NOT_EDITABLE`); approval is an atomic `findOneAndUpdate({ _id, status: 'DRAFT' })` so concurrent approvals cannot both win (the loser gets `409 EXPENSE_NOT_APPROVABLE`); voiding requires a reason (`400 EXPENSE_VOID_REASON_REQUIRED`) and is guarded against repetition (`409 EXPENSE_ALREADY_VOIDED`). **Amounts are immutable once approved** — a correction is a void plus a replacement record, never a rewrite. There is no delete route anywhere in the expense surface. `expenseNumber`, `totalAmount`, `status`, `statusHistory`, `createdBy`, `approvedBy`/`approvedAt`, `voidedBy`/`voidedAt`, and the timestamps are rejected by the strict allowlists rather than ignored. Successful transitions audit `EXPENSE_CREATED`, `EXPENSE_UPDATED`, `EXPENSE_APPROVED`, `EXPENSE_VOIDED`; refusals write nothing.

Revenue semantics are the Phase D definitions **reused, not redefined**, and `financeService` is their single owner: `grossSales` sums `order.total` for all orders; `realizedRevenue` sums only `DELIVERED` **and** `PAID`; `refunds` sums non-`FAILED` refunds from the existing `Refund` collection (no second finance-refund collection exists); `netSales = grossSales − refunds`; `grossProfit = netRealizedRevenue − COGS`; `operatingProfit = grossProfit − approvedExpenses`. Only `APPROVED` expenses are realized — `DRAFT` and `VOIDED` are reported for visibility and excluded from every total (`basis: APPROVED_EXPENSES_ONLY`).

**Cancelled orders are never realized revenue** and contribute no COGS or profit, while remaining visible in `grossSales` and the status breakdown. **Delivery never infers payment**: `updateOrderStatus` never touches `paymentStatus`, and the only `UNPAID → PAID` path is the explicit `PATCH /api/v1/admin/orders/:orderId/payment-status` (audits `ORDER_PAYMENT_UPDATED`). Until that call is made, a delivered COD order appears as `orders.unpaidCodOrders` / `unpaidCodValue` — quantified and excluded from revenue.

COGS uses the immutable per-line snapshot (`items.unitCost`, `items.lineCost`) taken at checkout on the `LATEST_PURCHASE_COST` basis, so a later `Product.costPrice` change cannot move historical profit. Lines predating snapshots carry no cost rather than a fabricated zero, and every COGS-bearing response states `cogsCoverage: { linesTotal, linesWithCostSnapshot, coverage, complete }`. **FIFO, LIFO, weighted average, and standard costing remain explicitly not implemented.**

`GET /api/v1/admin/finance/profit-loss` is a management summary (`basis: MANAGEMENT_PROFIT_AND_LOSS_SUMMARY`) whose bottom line is `operatingProfit` — **not** net income. It enumerates its own exclusions (`CORPORATE_INCOME_TAX`, `DEPRECIATION_AND_AMORTISATION`, `FINANCING_COSTS_AND_INTEREST`, `BANK_FEES_NOT_RECORDED_AS_EXPENSES`, `ACCRUALS_AND_PERIOD_CUT_OFF_ADJUSTMENTS`, `INVENTORY_WRITE_DOWNS_AND_SHRINKAGE`, `REFUND_COST_REVERSAL`) and states plainly that it is not a GAAP or IFRS statement, not audited, and not a substitute for statutory accounting or tax filing. Tax reporting is strictly what was recorded — sales tax on realized orders, tax on approved expenses, and their net — with **no jurisdiction rules, rate tables, exemptions, registration thresholds, filing, or compliance claim of any kind**.

**A `Payment` collection is deliberately deferred.** `Order.paymentStatus` plus the existing `Refund` collection already record everything a cash-on-delivery business can know, so a payment model would duplicate those facts without adding information. There is no payment-gateway abstraction, no provider adapter, no webhook handler, and no capture/settlement state machine — building one would pretend money moves externally when it does not. The payment provider remains **TBD / NOT CONFIRMED**, and no gateway SDK is present.

Endpoints: `GET|POST /api/v1/admin/expenses`, `GET /expenses/summary`, `GET /expenses/:id`, `PATCH /expenses/:id`, `PATCH /expenses/:id/status`, `GET /finance/dashboard`, `GET /finance/analytics`, `GET /finance/profit-loss`. All are `SUPER_ADMIN`-only; the legacy `/api/*` surface is removed.

## Reporting ERP

Full design notes live in [REPORTING_ARCHITECTURE.md](./REPORTING_ARCHITECTURE.md).

Ten `SUPER_ADMIN` reports under `GET /api/v1/admin/reports`, which is itself a self-describing index: `sales`, `products`, `inventory`, `inventory-movements`, `customers`, `orders`, `purchases`, `finance`, `profit`, `tax`. Every money figure comes from the same `financeService` functions the finance dashboard uses, so **the same window produces one set of numbers across the sales dashboard, finance dashboard, finance report, sales report, profit report, and profit-and-loss** — `realizedRevenue`, `refunds`, `netSales`, `grossSales`, COGS, gross profit, operating profit, and sales tax all agree, and the integration test asserts it across three ranges.

Three differences are intentional and documented rather than accidental: per-day `grossProfit` excludes refunds (a refund is a period fact subtracted once, not attributable to the original sale's day); line-level `realizedRevenue` excludes shipping and tax while order-level includes them; and `topSuppliers[].committedValue` includes `DRAFT` purchase orders while `purchaseOrders.committedValue` counts only live statuses.

Reports read immutable snapshots, so renaming a product, repricing it, changing its cost, or renaming a supplier leaves every historical revenue, item, COGS, and purchase-order figure byte-identical. Two things deliberately do move: `/reports/inventory` valuation, which is a current replacement-cost view of stock on hand (`valuationBasis: LATEST_PURCHASE_COST`, not FIFO/LIFO/weighted average), and supplier display labels, which identify a counterparty rather than state an amount.

Availability everywhere is aggregated from `InventoryBalance` (`quantityOnHand − quantityReserved`); `Product.stock` is never read by a report. `/reports/inventory` takes **no** date range — stock on hand is a point-in-time fact and a `from`/`to` pair would imply a historical reconstruction the ledger does not support — so a range parameter is `400 VALIDATION_ERROR` and the response carries `asOf`.

Every windowed report resolves its range through one function: a named `range` (`7d|30d|90d|180d|365d`, default `30d`) **or** an explicit `from`/`to` pair. Both together, a half pair, or reversed bounds are `400 RANGE_INVALID`; a span over `maxRangeDays` (366, advertised in every response) is `400 RANGE_TOO_LARGE`; an unparseable date or unknown named range is `400 VALIDATION_ERROR`.

Sort keys, group-by dimensions, and filters are fixed vocabularies — a real Mongo field name that is not whitelisted (`_id`, `createdAt`, `price`, `$natural`, `password`, `__proto__`) is rejected exactly like nonsense, and every sort is tie-broken by `_id` so paging is stable. Search input is regex-escaped, so `.*`, `^Report`, `(alpha|beta)`, and `\w+` match literally and return nothing rather than selecting the collection. Because every query schema is `.strict()` with per-field coercion, unknown keys and Mongo operator objects (`from[$gt]`, `search[$ne]`, `page[$gt]`) are `400`, and prototype-pollution attempts cannot reach `Object.prototype`.

Row reports share one envelope (`page`, `limit`, `total`, `totalPages`, `hasNextPage`, `hasPreviousPage`) with `limit` defaulting to 20 and capped at 100; `limit=0`, `limit=101`, `page=0`, negative, fractional, and non-numeric values are `400`, and a page past the end is an empty array with a truthful total. `/reports/profit` paginates only when grouped by `product` or `category`. A ratio with no denominator is `null`, never `0` — `grossMargin`, `operatingMargin`, `repeatRate`, `fulfilmentRate`, `cancellationRate`, `acceptanceRate`, and `cogsCoverage.coverage` all behave this way.

Reports perform no writes and aggregate the live collections — there is no reporting warehouse, no materialised summary collection, and no rollup job to fall out of sync. **Report export remains deferred**, and the index says so machine-readably: `export: { available: false, reason: … }`. No report can be downloaded as CSV or XLSX, and there is no scheduled delivery. The supplier CSV import below is inbound catalog data, not a reporting export; it adds no export capability to any report.

## CSV catalog import

Full design notes live in [CSV_CATALOG_IMPORT_ARCHITECTURE.md](./CSV_CATALOG_IMPORT_ARCHITECTURE.md).

**A supplier CSV can never publish a product.** Every product an import creates is `DRAFT` with `sellingPriceOverridden: false`, and no mapping target reaches `Product.status` or the storefront. Publication is a separate, explicit, audited admin act.

**A supplier CSV can never set the MansooriKart selling price.** The mapping targets write `SupplierCatalogItem.supplierCost`; there is no target for `Product.price`, and the update patch a repeat import builds does not contain `price`. A supplier's own MSRP, when supplied, lands in the separately named reference field `Product.supplierSuggestedRetailPrice`, which nothing computes from and nothing displays as the price.

Upload is `POST /api/v1/admin/catalog-imports` with the CSV as a raw body under a route-scoped `express.raw`; five content types are accepted (`text/csv`, `application/csv`, `text/plain`, `application/vnd.ms-excel`, `application/octet-stream`) and anything else is `415 CSV_CONTENT_TYPE_UNSUPPORTED`. There is no multer and no CSV dependency — the parser is `backend/src/utils/csv.ts`, RFC 4180 quoting included. Bounds are declared, not discovered: 5 MiB, 5,000 rows, 60 columns, 120-character headers, 2,000-character fields, 20 preview rows, and a 500-document write batch. Every parse failure is a stable client code (`CSV_EMPTY`, `CSV_NO_DATA_ROWS`, `CSV_NOT_TEXT`, `CSV_ENCODING_INVALID`, `CSV_TOO_LARGE`, `CSV_TOO_MANY_ROWS`, `CSV_TOO_MANY_COLUMNS`, `CSV_HEADER_MISSING`, `CSV_HEADER_BLANK`, `CSV_HEADER_DUPLICATE`, `CSV_HEADER_TOO_LONG`, `CSV_FIELD_TOO_LONG`, `CSV_QUOTE_INVALID`, `CSV_QUOTE_UNTERMINATED`), and an oversize body is `413 REQUEST_BODY_TOO_LARGE` from the parser before it is ever buffered; **parser internals never reach a client**, and an unrecognised fault degrades to `CSV_INVALID`.

The flow is upload → map → preview → import. Mapping is confirmed with `POST /catalog-imports/:id/mapping`; suggested and template mappings are offered by `GET /catalog-imports/mapping-targets`, and **unmapped columns are ignored entirely** rather than guessed at. `GET /catalog-imports/:id/preview` writes nothing at all and runs the same pure `mapRows` the import runs, so the preview an operator approves is the work that executes. Row outcomes are `CREATE` (new `DRAFT` product plus supplier source), `UPDATE` (cost, stock and availability refreshed), `SKIP` (nothing changed), or a per-row failure — a missing supplier SKU, a duplicate SKU inside the same file (**every occurrence fails**, not just the second), or a source whose product no longer exists. Existing descriptive fields are only rewritten when the operator opts in with `allowFieldOverwrite`, which defaults to false.

Image URLs are validated — HTTPS, bounded length, at most ten, private and link-local hosts refused — and **never fetched server-side**. Cell values are stored as literal text and never evaluated; the `csvSafeValue` helper neutralises formula-leading characters if a value is ever written back into CSV form, so an imported `=cmd|…` cell stays inert data.

`POST /catalog-imports/:id/import` claims the job with a single atomic transition out of `READY` (a second caller gets `409 IMPORT_IN_PROGRESS`, a completed job replays as `replayed: true`), then inserts in batches and verifies what landed. Completion status is honest rather than optimistic: no problems is `COMPLETED`, problems with nothing landed is `FAILED`, and anything else is `PARTIAL`. A cost change is _reported_ per row (`oldCost`, `newCost`, `difference`, `percentChange`) with a `CATALOG_IMPORT_COST_CHANGES` audit entry above 10%; the selling price is left exactly as the admin set it. **A supplier stock change is not an `InventoryMovement`** — supplier stock is the supplier's number, owned-stock inventory remains the `InventoryBalance` authority, and the two ledgers never mix.

Audit records `CATALOG_IMPORT_UPLOADED`, `CATALOG_IMPORT_MAPPED`, `CATALOG_IMPORT_COMPLETED`, `CATALOG_IMPORT_COST_CHANGES`, and `CATALOG_IMPORT_CANCELLED` — ids and counts only, **never CSV contents**. No supplier credential, portal URL, or API key is stored anywhere in the import surface.

## Pricing

Full design notes live in [PRICING_ARCHITECTURE.md](./PRICING_ARCHITECTURE.md).

**A supplier controls their cost; MansooriKart controls the selling price.** The pricing engine only ever computes a _suggestion_ — writing `Product.price` is always an explicit caller act through `POST /api/v1/admin/pricing/apply`, a direct admin catalog update, or the initial price of a new draft when the operator opted in at mapping time.

`PricingRule` scopes on `supplier`, `category`, `brand`, and a `minCost`/`maxCost` band, all optional and **ANDed** — an empty field matches anything, a populated one must match. Computation order is fixed and documented because operators reconcile these numbers by hand: markup (`PERCENTAGE` 25 means +25%, `FIXED` is an absolute amount), then the `minimumProfit` floor, then rounding. `END_99` lowers a price to the largest value ending in 99 at or below it and is **skipped entirely when it would breach the profit floor**; the response reports `appliedMinimumProfit` and `appliedRounding` so an operator sees which steps moved the number. `markupValue` and `minimumProfit` are non-negative by schema, so **a computed price is always at least cost** — the engine cannot author a negative margin. An unusable cost is `400 PRICING_COST_INVALID` and a computed price above the 100,000,000 ceiling is `400 PRICING_PRICE_TOO_LARGE` rather than a stored absurdity.

When several active rules match, exactly one wins, deterministically: scope specificity (`supplier` 8 + `category` 4 + `brand` 2 + cost band 1, summed), then `priority` descending, then the older rule, then id. **Two rules can never tie**, selection never depends on driver document order, and there is no "first match wins" anywhere. A disabled rule is invisible to the engine, and applying one explicitly is `400 PRICING_RULE_INACTIVE`. An inverted cost band is `400 PRICING_RULE_COST_BAND_INVALID`; a rule scoped to a non-existent supplier is `400 PRICING_RULE_SUPPLIER_NOT_FOUND`.

**A manual price survives everything.** `Product.sellingPriceOverridden` marks a price a human decided; a bulk run reports such a product as `PRICE_MANUALLY_OVERRIDDEN`, counts it in `summary.preservedOverrides`, and leaves it alone unless the request carries the explicit `includeOverridden: true` opt-in. A later supplier cost import does not disturb it either — cost, stock, and availability refresh while the selling price stays as the admin set it.

`POST /api/v1/admin/pricing/preview` and `/pricing/apply` are two requests over one computation. Targets are product ids (max 1,000, no duplicates) or a `supplierId`/`status`/`fulfillmentType` filter; selecting nothing is `400 PRICING_TARGETS_REQUIRED`, so there is deliberately no way to reprice the whole catalogue by omission. Per-product problems are row issues (`SUPPLIER_COST_MISSING`, `PRICING_RULE_NOT_MATCHED`, `PRICE_MANUALLY_OVERRIDDEN`), never throws, so one unpriceable product cannot abort a batch. `preview` writes nothing; `apply` writes only the changed rows in a single `bulkWrite`, sets `sellingPriceOverridden: true` on each, and **never touches `status`** — no pricing operation can publish anything.

Every margin figure exposed is **gross merchandise margin** (`sellingPrice − supplierCost`, over `sellingPrice`), and the label travels with the payload as `marginBasis: 'gross merchandise margin'`: it excludes shipping, payment fees, returns, refunds, and all operating expense, and is **not final business profit**. Finance remains the profit authority, and the dropship cost snapshot feeds the same COGS mechanism own-stock lines use, so there is one profit formula. Margin fields appear only on `SUPER_ADMIN` surfaces — **no customer-facing serializer exposes `supplierCost`, margin, or any pricing-rule internal**.

Rules are `POST|GET /api/v1/admin/pricing-rules`, `GET|PATCH /pricing-rules/:id`, and `POST /pricing-rules/:id/disable|enable`; `createdBy`, `updatedBy`, and `isActive` are rejected as input. Listing is ordered exactly as the engine resolves, so the list reads as the rule book it is. Audit records `PRICING_RULE_CREATED|UPDATED|DISABLED|ENABLED` and `PRICING_BULK_APPLIED` — rule metadata and counts, never a computed price list. Currency conversion (all amounts are PKR), competitor or dynamic repricing, scheduled runs, and per-customer price lists are deferred.

## Dropshipping and publication

Full design notes live in [DROPSHIPPING_ARCHITECTURE.md](./DROPSHIPPING_ARCHITECTURE.md).

**This is not a marketplace.** There is no supplier login, no supplier-facing API, no payout, no commission, and no settlement — a supplier is the existing operational contact record from Purchasing, and MansooriKart alone owns the catalogue, the price, and the customer relationship.

**There is one canonical `Product`.** No `DropshipProduct`, no `AdminProduct`, no parallel catalogue: an existing field, `fulfillmentType: OWN_STOCK | DROPSHIP`, says how a line is fulfilled, and every catalog, cart, checkout, order, review, and reporting path keeps working unchanged. `SupplierCatalogItem` (unique on `{ supplier, supplierSku }`) carries the sourcing facts — supplier SKU, cost, supplier stock, supplier availability, `lastSyncedAt` — and is **the only home for supplier stock**. `Product.sku` stays server-owned `MK-…` and is never taken from a supplier file, so a supplier renaming their SKU cannot rename a MansooriKart product or move an order's identity.

**Supplier stock is advisory, owned stock is authoritative.** A dropship line never reserves, decrements, or restores `InventoryBalance`, and no `InventoryMovement` is written for it — the warehouse ledger continues to describe only goods MansooriKart holds. Supplier numbers are labelled with their age (`SUPPLIER_STOCK_STALE_AFTER_HOURS` 48, `SUPPLIER_LOW_STOCK_THRESHOLD` 5) and **an `UNKNOWN` or stale figure never blocks a sale** — refusing an order on a number nobody vouches for would be worse than accepting it. Only an explicit `OUT_OF_STOCK` from the supplier blocks: cart writes return `409 SUPPLIER_OUT_OF_STOCK` or `409 SUPPLIER_UNAVAILABLE` (own stock returns `409 INSUFFICIENT_STOCK`) and checkout returns `409 DROPSHIP_UNAVAILABLE` (own stock `409 STOCK_UNAVAILABLE`).

**A mixed order is normal.** One order may contain own-stock and dropship lines across several suppliers, and each line freezes what was true at purchase: `fulfillmentType`, and for dropship lines `supplier`, `supplierSku`, and `supplierCost`, plus `unitCost` (`supplierCost` for dropship, `Product.costPrice` for own stock) and `lineCost`. A later cost import, supplier rename, or repricing therefore cannot move a historical order, invoice, COGS figure, or profit number.

Checkout creates one `DropshipFulfillment` per supplier in the order — `DSF-YYYYMMDD-XXXXXX`, server-generated, unique on `{ order, supplier }` — under the same `Idempotency-Key` as the order, with compensation if persistence fails, so a replay produces exactly one fulfilment per supplier and never a duplicate obligation. When several sources could supply a line, the choice is deterministic (lowest cost, then oldest, then id), so a pricing preview and the order snapshot never disagree about which supplier is in play.

A fulfilment moves `PENDING → SENT_TO_SUPPLIER → SUPPLIER_CONFIRMED → SHIPPED → DELIVERED`, with `CANCELLED` and `FAILED` as terminal exits. Every transition is claimed with one atomic conditional update: a concurrent pair yields exactly one winner and `409 DROPSHIP_FULFILLMENT_CONFLICT` for the loser, an illegal hop is `400 DROPSHIP_TRANSITION_INVALID`, and re-sending the current status is an idempotent no-op that writes no history. **Fulfilment status is independent of `Order.orderStatus`** — shipping a supplier's parcel does not silently ship the customer's order, and the two are reconciled by an operator rather than inferred. Tracking accepts a bounded carrier and number with an HTTPS `trackingUrl` (`400 TRACKING_URL_INVALID`) that is stored for humans and **never fetched server-side**. Cancellation records MansooriKart's own intent only: `requiresSupplierContact` is false only from `PENDING`, and the response says plainly that no supplier was contacted — no API call, email, or webhook leaves the system.

A `DropshipFulfillment` is an obligation on someone else's stock; a `PurchaseOrder` plus `GoodsReceipt` is an acquisition of MansooriKart's own. They are deliberately separate collections: only the purchasing path moves `InventoryBalance`, only it writes `PURCHASE_RECEIPT` movements, and only it updates `Product.costPrice`. Nothing in this phase changes that.

**Publication is a backend gate, not a UI convention.** `Product.status` is `DRAFT → ACTIVE → ARCHIVED`, and public catalog reads remain active-only, so a draft is structurally absent from the storefront rather than merely hidden by a frontend that could be bypassed. `POST /api/v1/admin/products/:id/publish` validates before it promotes and returns **every** blocking reason at once — `NAME_REQUIRED`, `SKU_REQUIRED`, `DESCRIPTION_REQUIRED`, `IMAGE_REQUIRED`, `PRICE_REQUIRED` (a zero price fails), `CATEGORY_REQUIRED`, `CATEGORY_ARCHIVED`, `FULFILLMENT_TYPE_INVALID`, and for a dropship product `SUPPLIER_SOURCE_REQUIRED` — rather than one error per attempt. `POST /products/publish-preview` answers "what would happen" without writing, `POST /products/publish` and `/products/archive` are bulk and capped at 200 unique ids (`PRODUCT_IDS_REQUIRED`, `PRODUCT_IDS_TOO_MANY`, `PRODUCT_IDS_DUPLICATE`), and both return a per-product verdict so one unpublishable product leaves the rest untouched instead of throwing the batch away. Creating or patching a product straight into `ACTIVE` passes the identical gate, so the CRUD routes are not a second door onto the storefront. **No import, pricing run, or fulfilment transition can publish anything.**

Customer-facing order and cart payloads expose exactly `productId`, `name`, `sku`, `image`, `unitPrice`, `quantity`, and `lineSubtotal`. **A customer never learns that a line is dropshipped, who the supplier is, what it cost, or what the margin was** — `fulfillmentType`, `supplier`, `supplierSku`, `supplierCost`, `unitCost`, and `lineCost` are all absent from every public serializer, and the admin order detail is where they appear alongside the order's `dropshipFulfillments`.

Admin routes are `SUPER_ADMIN`-only. Supplier sources are **read-only** — `GET /api/v1/admin/supplier-sources`, `/supplier-sources/:id`, and `/products/:productId/supplier-sources` — because cost and stock arrive from a supplier file rather than being typed in. Fulfilments are `GET /dropship-fulfillments`, `/:id`, and `/cancellation-policy` plus a single `PATCH /dropship-fulfillments/:id` whose strict body is `status`, `supplierOrderReference`, `supplierTrackingNumber`, `carrier`, `trackingUrl`, `notes`, and `reason` and nothing else. **There is no route that creates a fulfilment by hand** — a fulfilment exists because a customer bought something — so `POST /dropship-fulfillments` is a 404, and server-owned fields (`fulfillmentNumber`, `order`, `orderItems`, `supplier`, `status` history, every stage timestamp, cost snapshots) are rejected by the allowlist rather than ignored. Audit records `DROPSHIP_FULFILLMENT_CREATED`, `DROPSHIP_FULFILLMENT_STATUS_CHANGED`, `DROPSHIP_FULFILLMENT_TRACKING_UPDATED`, `PRODUCT_PUBLISHED`, `PRODUCT_BULK_PUBLISHED`, `PRODUCT_ARCHIVED`, and `PRODUCT_BULK_ARCHIVED`.

Deferred deliberately: supplier portals and logins, supplier API or EDI integration, automated purchase-order transmission, supplier-side stock webhooks, shipping-carrier tracking lookups, supplier invoicing or payouts, commission and margin settlement, multi-currency supplier costs, and all frontend work.

## Marketing and merchandising

Full design notes live in [MARKETING_ARCHITECTURE.md](./MARKETING_ARCHITECTURE.md).

**There is one discount authority, and it is the existing `Coupon` model validated at checkout.** No second coupon system was created. `/api/v1/admin/coupons` is a management API over that same collection: it lists, filters, creates, edits, activates, disables, soft-archives, and reports usage, and **it never computes a discount** — `orderService.couponFor` remains the only code that decides what a customer pays, unchanged. Codes normalize to uppercase and a duplicate is `409 COUPON_CODE_EXISTS` raised from the unique index. Negative or zero values, percentages above 100, inverted date ranges, non-positive limits, negative minimums and oversized strings are all `400 VALIDATION_ERROR`; `usageCount`, `_id`, `createdAt`, `updatedAt` and `createdBy` appear in no schema. **Editing a coupon never rewrites an order's coupon snapshot** — each order froze `couponId`, `code`, `type`, `value` and `actualDiscount` at checkout — so renaming or repricing a coupon leaves every historical order and every usage statistic byte-identical. Lifecycle state (`ACTIVE`, `SCHEDULED`, `EXPIRED`, `EXHAUSTED`, `DISABLED`) is **derived** from `enabled`, the date window and `usageCount` versus `usageLimit`; it is not a stored field that could disagree with the coupon it describes. DELETE is a soft disable returning `{ id, archived: true }`, because redemptions and order snapshots reference the record.

`Promotion` is a merchandising announcement, **not** a second discount authority. It has no percentage, amount, stacking rule or eligibility field, and no code path lets a promotion change a total; `couponCode` on a promotion is display text advertising a code the customer may type, which checkout still resolves against `Coupon` as it always has. Statuses are `DRAFT`, `SCHEDULED`, `ACTIVE`, `EXPIRED`, `ARCHIVED`, and public visibility is **derived at read time** from status plus the `startAt`/`endAt` window — so there is no scheduler, no cron job and no way for a client to request a promotion the window excludes. The window is half-open (`startAt <= now`, `endAt > now`), so a promotion that expires this second is already gone.

Banners are placed in `HOME_HERO`, `HOME_PROMO` or `CATEGORY_HERO`. Destinations are structured rather than free strings: `linkType` selects `NONE`, `INTERNAL_PATH`, `PRODUCT`, `CATEGORY`, `PROMOTION` or `EXTERNAL_URL`, and the route validates the matching field. An external URL must parse as absolute with a hostname and an `http:`/`https:` scheme, so `javascript:`, `data:` and `file:` are rejected; an internal path must be a single-leading-slash relative path with no `//`, `:`, `..`, backslash or markup character. **No image or link URL is ever fetched server-side** — every one is validated structurally and handed to the client as-is. Public banner reads return only currently visible records, and `status`, `priority`, `startAt` and `endAt` are absent from the payload.

`GET /api/v1/store/home` is a single bounded aggregation over a curated `HomepageConfiguration`: a closed section vocabulary (`HERO`, `FEATURED_PRODUCTS`, `NEW_ARRIVALS`, `BEST_SELLERS`, `FEATURED_CATEGORIES`, `PROMOTION`, `BANNER`, `TRUST_FEATURES`) with per-section caps, **not** a free-form page builder. Eligibility is applied in the query rather than after serialization: only `status: 'ACTIVE'` products, `ACTIVE`-or-absent categories and in-window banners are ever loaded, so **a `DRAFT` supplier-import product is structurally unable to reach the homepage**. A reference whose target is missing or ineligible degrades to `{ type: 'NONE' }` rather than emitting a dead link or revealing that a hidden record exists. `PUT /homepage` and `POST /banners/reorder` replace whole ordered lists, because patching an order entry-by-entry lets two concurrent edits interleave into an arrangement neither operator asked for.

Marketing audit actions are `COUPON_CREATED|UPDATED|ENABLED|DISABLED|ARCHIVED`, `PROMOTION_CREATED|UPDATED|ACTIVATED|ARCHIVED`, `BANNER_CREATED|UPDATED|ACTIVATED|ARCHIVED|REORDERED`, and `HOMEPAGE_UPDATED|SECTION_TOGGLED`. A PATCH whose submitted values match the stored ones writes no entry.

## Content: CMS pages, FAQs and navigation

Full design notes live in [CMS_ARCHITECTURE.md](./CMS_ARCHITECTURE.md).

**No HTML is stored, so none needs sanitising at render time.** A page body is a bounded array of typed blocks over a closed vocabulary — `HEADING` (levels 2–4; `h1` belongs to the page title), `PARAGRAPH`, `LIST`, `QUOTE`, `IMAGE`, `DIVIDER` — validated by a Zod discriminated union whose every branch is `.strict()`, capped at 120 blocks. There is no `html`, `raw`, `script`, `style`, `template` or `embed` field anywhere in the union, and **no arbitrary executable script or template code can be stored or rendered**. Every text field runs through a `stripMarkup` transform _during validation_, so sanitisation cannot be forgotten by a route author: `<script>` and `<style>` elements are removed with their contents (`<script>alert(1)</script>` leaves nothing behind, not `alert(1)`), remaining tags are stripped, entities that could reintroduce a bracket are neutralised, and control characters are dropped.

Slugs are unique, lowercase, `^[a-z0-9]+(?:-[a-z0-9]+)*$`, at most 120 characters, and may be derived from the title; a collision is `409 PAGE_SLUG_EXISTS` from the unique index rather than a prior read, so concurrent creates cannot both succeed, and a title yielding no usable slug is `400 PAGE_INVALID`. Status is `DRAFT`, `PUBLISHED`, `ARCHIVED`; `publishedAt` is stamped the first time a page is published and **never rewritten**, so editing published text or re-publishing after an archive preserves the original date. DELETE is a soft archive. **CMS pages record the store's current policy and carry no legal versioning**: the five policy documents (shipping, returns, refunds, privacy, terms) are ordinary CMS pages, and what a past customer agreed to lives in that customer's own immutable order snapshot — editing the returns page changes what the next visitor reads and nothing about any order already placed.

FAQs are `question`, `answer`, `category` (default `General`), `position` and `DRAFT|ACTIVE|ARCHIVED`. `POST /faqs/reorder` verifies every id then rewrites positions in one `bulkWrite`, and is declared before `/faqs/:id` so the literal path wins over the parameter. The category filter is an anchored, case-insensitive, `escapeRegex`-escaped exact match, so `General` does not also match `General knowledge` and `.*` matches literal characters.

Navigation is one singleton document per menu (`HEADER`, `FOOTER`) with a unique index on `menu`, capped at 30 items and 20 children each. **Depth stops at one level of children structurally** — the child schema has no `children` key — so no unbounded recursive tree can be submitted. Destinations use the same structured, scheme-validated shape as banners (`INTERNAL_PATH`, `CATEGORY`, `PRODUCT`, `CMS_PAGE`, `EXTERNAL_URL`). References are checked for **existence** at write time (`400 REFERENCE_NOT_FOUND`, listing offenders as `field:id`) and for **eligibility** at read time, so an operator may legitimately wire a menu to a product that is still `DRAFT`, and the public menu simply omits that entry until it is published — **draft or archived products and unpublished CMS pages are never serialized into a public menu**. `PUT /navigation/:menu` replaces one menu whole; an unknown menu name is `404 MENU_NOT_FOUND`, checked against a fixed set before anything is read.

`GET /api/v1/store/pages/:slug` requires a well-formed slug and matches `status: 'PUBLISHED'` in the query itself, so a draft page, an archived page, an unknown slug and a malformed slug all return the identical `404 PAGE_NOT_FOUND` — the endpoint cannot be used to enumerate unpublished pages. Public page payloads carry `slug`, `title`, `excerpt`, blocks, an `seo` object with sensible fallbacks, and timestamps; `status`, `createdBy`, `updatedBy` and internal ids are absent. Content audit actions are `CMS_PAGE_CREATED|UPDATED|PUBLISHED|ARCHIVED`, `FAQ_CREATED|UPDATED|ARCHIVED|REORDERED` and `NAVIGATION_UPDATED`, recording slugs and changed field names — never the content itself.

## Store configuration

Full design notes live in [STORE_CONFIGURATION_ARCHITECTURE.md](./STORE_CONFIGURATION_ARCHITECTURE.md).

`StoreConfiguration` is **one singleton document**, pinned by a unique index on a `key` field whose enum contains the single value `STORE`. `ensureStoreConfiguration()` awaits `init()` so the index exists, then upserts with `$setOnInsert` and re-reads on duplicate-key `11000` — so **concurrent initialisation cannot create a second configuration**; the loser of the race reads the winner's document instead of inserting its own.

Settings are **typed sections, not a generic `key/value: any` bag**: `store`, `contact`, `social`, `seo`, `shipping`, `tax`, `invoice`, `email` and `maintenance`, each with its own `.strict()` Zod schema and numeric bounds. A PATCH edits individual keys within one section — omitting a key leaves it alone rather than resetting it to a default — and each handler diffs the submitted values against the stored ones, so a no-op PATCH writes nothing and audits nothing.

Currency defaults to **PKR** and **relabels only**: there is no exchange-rate table, no conversion and no per-currency price, so changing the label never restates a stored amount. Timezone defaults to **Asia/Karachi**, is validated by constructing an `Intl.DateTimeFormat` with it, and is a **display clock only** — every timestamp remains UTC in Mongo, so **changing the timezone never rewrites a historical timestamp**. Contact settings hold an email, a bounded phone, an address and a country defaulting to `Pakistan`. Social links are a closed six-channel set (`FACEBOOK`, `INSTAGRAM`, `TIKTOK`, `YOUTUBE`, `LINKEDIN`, `X`), each URL validated as absolute `http:`/`https:`, replaced as a whole list with duplicate channels rejected.

SEO holds `metaTitle`, `metaDescription`, an `http:`/`https:` `canonicalUrl`, a social image, an OpenGraph title/description and `robots` from a **fixed four-value enum** (`index,follow`, `index,nofollow`, `noindex,follow`, `noindex,nofollow`) — never a free string. Every SEO text field passes through the plain-text transform that drops CR and LF, so **no configured value can inject a response header**; the Twitter handle is `^@?[A-Za-z0-9_]{1,15}$`.

**Shipping configuration is what checkout actually charges.** `quoteShipping` applies, in order: disabled → 0; discounted subtotal at or above the free-shipping threshold (`>=`, so the boundary is free) → 0; a city override matching the server-loaded address city → that fee; otherwise the standard fee. The defaults — PKR 250 standard, free at PKR 5,000 — reproduce pre-Phase-H behaviour exactly, and an operator changing them changes the next checkout. **No client-supplied shipping value is read anywhere**, and orders keep their own snapshot, so a fee change never restates an order already placed. `codEnabled: false` makes checkout reject `CASH_ON_DELIVERY` with `PAYMENT_METHOD_UNAVAILABLE`; it defaults to true and **COD continues to work unchanged**.

Tax is a **foundation, disabled by default**: `enabled`, `defaultRate` (0–100), `pricesIncludeTax` and `displayTaxSeparately`, with no jurisdiction engine, no per-product class and no address-based rate. `computeTax` returns 0 when disabled, when prices already include tax, or when the rate is non-positive — so the shipped default preserves the previous zero-tax totals exactly. **No customer-supplied tax value is ever accepted.** Invoice settings are presentation only — prefix, company details, footer note, terms text — and **cannot alter an order's immutable stored totals**; there is no second invoice engine, only configuration around the existing PDF.

Email settings hold **behaviour, never credentials**: a from-name, a from-address, a reply-to, and per-notification booleans. The schema is `.strict()`, so a request containing `smtpPassword`, `apiKey` or any other secret field is `400 VALIDATION_ERROR` — **SMTP passwords and provider secrets stay in environment/deployment secrets and are never stored in MongoDB**.

`maintenanceMode` closes public content, not the building. When it is on, the seven public content routes return `503 STORE_MAINTENANCE` with the configured safe message, while `GET /api/v1/store/config` still returns 200 (a maintenance page needs the store name and message to render), and **health endpoints and every Super Admin route are unaffected** — an operator can always authenticate and fix the system they closed.

`GET /api/v1/store/config` is served by an explicit allowlist serializer publishing only customer-safe values: store identity, contact, social links, SEO, currency and timezone labels, the shipping fee and free-shipping threshold, whether tax is displayed, and the maintenance flag and message. Internal ids, `key`, `createdBy`/`updatedBy`, tax internals, invoice settings, email settings and low-stock thresholds are all withheld. Configuration is read per request, so **a change takes effect without a restart**. Audit actions are `SETTINGS_UPDATED`, `MAINTENANCE_MODE_ENABLED` and `MAINTENANCE_MODE_DISABLED`, recording the section and changed field names.

## System operations

Full design notes live in [SYSTEM_OPERATIONS_ARCHITECTURE.md](./SYSTEM_OPERATIONS_ARCHITECTURE.md).

The Phase A public health endpoints are **unchanged**: `GET /health` returns `{ "status": "ok" }` and `GET /api/v1/health` returns the same status in the standard envelope. That is deliberately the whole payload — no version, no environment, no database state. `GET /api/v1/admin/system/health` is the operator's view behind `requireAuth` and `requireSuperAdmin`, reporting API status, database connectivity and its readyState label, uptime in seconds, an environment label, a version string, whether the store configuration exists, whether maintenance mode is on, and three named checks. Both health routes are exempt from maintenance mode.

**Nothing is read from the environment and echoed.** `environment` is narrowed against `['development','test','production']` and falls back to `development` for an unrecognised `NODE_ENV`; `version` comes from an explicit `APP_VERSION` and falls back to the literal `unknown` rather than reading `package.json` off disk. `database` is derived from `mongoose.connection.readyState` — **the connection string, its host, credentials and database name appear nowhere** — and `store.configured` is a boolean, not the configuration. No branch emits a stack trace: failures reach the shared error middleware and its two-key `{ code, message }` envelope. A disconnected database is not an error but `status: 'degraded'` with a 200, because the API is answering and saying so accurately is what a console needs. Note one documented side effect: admin health calls `getStoreConfiguration()`, which initialises the singleton.

**There is one audit authority and Phase H added no second audit model.** `/audit-logs` exposes three GETs and nothing else — no POST, PATCH, PUT or DELETE anywhere in the router — so records are **append-only structurally**, not by policy, and no admin client can rewrite history through this API. The list accepts `page`, `limit`, `action`, `resourceType`, `resourceId`, `actor`, `search`, `sort`, `from` and `to` under a `.strict()` schema. None of those reaches the query language: `actor` must match 24-hex, `sort` is an enum mapped to a fixed `createdAt` direction, and `search` is an escaped, anchored prefix regex over `action` only — so `.*` finds nothing instead of everything. The date range is validated as a range: `from` may not follow `to`, and the span may not exceed 366 days, which is what stops an admin token being a denial-of-service. Pagination is mandatory and bounded (default 20, cap 100) with `total`, `totalPages`, `hasNextPage` and `hasPreviousPage`; `/audit-logs/actions` is declared before `/audit-logs/:id` and caps its vocabulary at 500 actions and 200 resource types. A malformed id is checked with `isObjectId` first and returns the same clean `404 AUDIT_LOG_NOT_FOUND` as an id that does not exist.

Because `metadata` is `Mixed` and written by call sites across every phase, `redactAuditMetadata` runs on **every** entry the API returns. It matches key names case-insensitively as substrings — covering `pass`, `secret`, `token`, `jwt`, `authorization`, `cookie`, `apikey`, `credential`, `smtp`, `mongo`, `connectionstring`, `privatekey`, `signature`, `sessionid`, `otp`, `hash`, `salt`, `rawcsv`, `csvbody`, `filebody` and `env` — so `smtpPassword`, `x-api-key`, `refreshToken`, `supplierCredential` and a future `providerSecretV2` are all caught without maintaining an exhaustive list. **Password hashes, JWTs, environment secrets, raw CSV bodies, supplier credentials and sensitive request headers therefore cannot be published through the audit API.** Structure is bounded too — strings truncate at 512 characters, objects publish 40 keys, arrays 20 items, recursion stops at depth 4 — and anything past a bound is summarised (`[TRUNCATED]`, `[N more]`) rather than dropped silently. `actor` is populated with the projection `'name email role'`, so the password hash is never loaded in the first place.

The same router serves the console's pre-existing dashboard reads — counts with two short lists, plus range-scoped sales, order and product aggregations whose `range` is an enum of `7d`, `30d`, `90d` rather than a pair of dates, with the boundary computed in UTC. Revenue counts `DELIVERED` and `PAID` orders and groups on stored fields, so **changing the delivery fee or enabling tax does not restate yesterday's revenue**.

Deferred deliberately across Phase H: email, SMS and push campaigns, marketing automation, affiliate, loyalty and referral programmes, ad-platform integrations, AI marketing generation; a WYSIWYG or drag-and-drop page editor, arbitrary HTML or template code in content, scheduled publication workers, content versioning and revisions, multi-language content, media library and uploads, blog domains; multi-currency and conversion, a tax-jurisdiction engine, per-product tax classes, a second invoice engine, credential storage in MongoDB; log shipping, metrics and tracing endpoints, alerting, audit retention/archival/export, audit write APIs of any kind; Google OAuth, payment-provider integration, marketplace/vendor functionality, and all frontend work — no customer storefront UI and no Super Admin frontend were built.
